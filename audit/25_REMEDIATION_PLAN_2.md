# Remediation plan II — what Phases 48, 49 and 50 found

The first plan (`22_REMEDIATION_PLAN.md`) fixed the audit's findings and
shipped as v15.0.0. This one addresses what attacking that work found.

**Organised by class, not by file.** The first plan's most useful property was
that R11 and R13 prevented the *next* instance rather than fixing the current
one; the same ordering applies here. **S1 and S2 come first** because they
change what every number in this product means.

Every task states its RED-CHECK: the narrowest mutation that must be observed
failing (CLAUDE.md, K7).

# P1 — The numbers must mean something

## S1 · Reading a counter must not change it

**Finding (P50-N1, U-01):** `llm-router doctor --audit` increments
`fail_open_events` by 4 per run. Measured on published 15.0.0: 4 → 8 → 12
across three read-only invocations.

**This invalidates published numbers.** The R12 commit message and
`audit/REMEDIATION_RUN.md` both report `fail_open_events: 713, of which
CHZ-FO-COST-MIGRATE-ALTER = 531` as a finding about the product. A share of it
was generated by running `doctor` during development, and the share is
unrecoverable — a contaminated counter cannot be cleaned up retroactively,
only reset and re-measured after S1 and S2 land.

### Acceptance criteria

1. Any diagnostic read (`doctor`, `doctor --audit`, `status`, the counter
   registry's `readings()`) leaves every counter unchanged. Asserted by reading
   twice and comparing, for EVERY registered counter — not just the one found.
2. A counter that a diagnostic path can increment is either moved off that path
   or documented in the registry with an explicit `observer_effect` note, and
   the note is checked.
3. The commit messages and `audit/` documents carrying the contaminated figures
   are corrected in the same change, with the corrected basis stated.

**RED-CHECK:** add a `failopen.record()` to any code path `doctor --audit`
walks → the read-twice test fails naming the counter.

**Precedent to copy:** `hook_liveness.orphan_count()` already refuses to reap,
and `test_reading_the_count_does_not_change_it` pins it. The rule existed for
one counter and was never generalised. Generalise it.

## S2 · A counter's zero must be reachable in normal operation

**Finding (U-02, P50-N2):** `CHZ-FO-COST-MIGRATE-ALTER` fires twice per
database open because an idempotent migration no-ops with `duplicate column
name`. That is correct behaviour recorded as a swallowed failure, and it is the
loudest code in the counter.

A counter whose baseline is normal operation cannot signal abnormal operation.

### Acceptance criteria

1. On a freshly created database with no faults injected, **every** counter in
   `counter_registry.REGISTRY` reads zero. A non-zero baseline is a defect in
   the counter, not a fact about the machine.
2. `_migrate_alter` treats "the column already exists" as SUCCESS, not as a
   swallowed failure — on every path, not only the regex-matched one.
3. Each registry entry states what a NON-ZERO value means operationally.
   R12 asked "does anyone read it"; this asks "should anyone act on it".

**RED-CHECK:** make an idempotent migration record a fail-open again → the
fresh-database baseline test fails naming the code.

## S6 · One migration per column

**Finding (P50-N2):** six `ALTER TABLE … ADD COLUMN is_simulated` statements
across `cost.py` (five) and `hooks/session-end.py` (one), each with its own
try/except. This is the CLASS-B shape the first plan's R11 was built to kill,
in the column that R6 added.

**Acceptance criteria:** one declaration per column, one applier, and an AST
test that fails on a second `ADD COLUMN` for a column already declared.

**RED-CHECK:** add a duplicate `ADD COLUMN` for an existing column → named.

# P2 — Mechanisms that disagree with each other

## S3 · The two routing layers must agree, or say why not

**Finding (U-03), observed live:** UserPromptSubmit injected *"CONTEXT-DEPENDENT
PROMPT — a stateless routed model cannot see this"* while PreToolUse
simultaneously held `Bash` with a HARD directive for the same turn. The request
was to read this machine's git state — something no external model can perform.

Every audit phase treated routing as one decision. It is at least two, in
different processes, with different inputs, and nothing compares them.

### Acceptance criteria

1. A test feeds the same prompt to both layers and asserts their verdicts are
   compatible: **PreToolUse must not hold a tool for a prompt UserPromptSubmit
   classified as context-dependent.**
2. The corpus covers the shapes that provoked it: a local shell command, a
   repo-state question, a question about the current conversation.
3. Where they legitimately differ, the difference is declared in one place both
   layers read.

**RED-CHECK:** make UserPromptSubmit mark a prompt context-dependent while
PreToolUse holds it → the parity test fails.

**Note on generality:** this is R10's class — refuse what cannot be served —
inverted. R10 stopped the gateway silently accepting requests it could not
serve; this is enforcement blocking a request only the local tool can serve.

## S4 · Price the escape hatch

**Finding (U-04), measured:** the documented escape — *"call ANY llm_* tool,
even a trivial `llm(task="query")`"* — routed `"Reply with the single word:
acknowledged"` to **qwen3-coder:30b**, which then held **42.6% of system
memory** and OOM-killed three background jobs including the pre-release
verification.

A cost-saving product whose escape hatch costs more than the thing it escapes.

### Acceptance criteria

1. The escape valve resolves to the cheapest available tier regardless of the
   held task's classification, or it does not load a model at all.
2. A test asserts the escape path's model selection, so "trivial query" stays
   trivial.
3. `doctor` reports resident model memory when a local backend is loaded —
   the OOM was invisible until three jobs died.

**RED-CHECK:** route the escape query and assert the chosen model is not the
`best`/`code` tier → fails if the escape inherits the held task's tier.

# P3 — Surfaces

## S5 · Audit and diagnostic output is a data-handling surface

**Finding (U-06):** an audit artifact named one of the operator's other private
projects with its filesystem path, in a PUBLIC repository. `check_identity.py`
caught it. The K1 generator then reproduced the class by printing
`sys.executable` (`/Users/<name>/…`) and was caught only because the privacy
assertion was written before the generator was trusted.

### Acceptance criteria

1. `scripts/check_identity.py` runs over `audit/` and over every generated
   report in CI, not only over source.
2. Any tool that WRITES a report redacts home paths at the point of writing —
   `freeze_state.py` does; nothing else was checked.
3. A test asserts no file under `audit/` contains an absolute home path.

**RED-CHECK:** write a home path into an `audit/` file → CI fails naming it.

## S7 · Rendered output must be rendered

**Finding (P50-N3):** `llm-router status` emits one line of literal rich markup
(`[bold #7aa2f7]…[/]`) on a clean install of 15.0.0 — a string printed with
`print()` rather than the rich console, on the first command the README sends a
new user to.

**Acceptance criteria:** a clean-room test asserts no output line contains
unrendered markup tokens, across `status`, `doctor` and `doctor --audit`.

**RED-CHECK:** `print("[bold]x[/]")` anywhere in those paths → named.

## S8 · Word order must not change the route

**Finding (K4, U-01 revalidated):**

    'what is 17 * 3?'         -> query     'tell me what 17 * 3 is'  -> ANALYZE

Not politeness, not length — a literal `what is` bigram. The fallback is the
MORE EXPENSIVE tier, so the failure mode is silently upgrading trivial
questions, and nothing reports it because it looks like an ordinary route.

**Acceptance criteria:** the classifier's decision is stable under word-order
paraphrase for a corpus of semantically identical pairs, EVALUATED ON THE
TARGET DISTRIBUTION rather than on the pair that found it. CLAUDE.md: a
one-point calibration is a guess; a proxy split has already misled by 4.25
points.

**RED-CHECK:** the existing `xfail(strict=True)` in
`test_k4_adversarial_corpus.py` XPASSes → the suite fails, forcing the corpus
and the docs to be updated together.

# Implementation record — what doing it found

Written after implementing S1, S2, S3, S5, S6 and S7. Shipped as v15.0.1.

## S1/S2/S6 — DONE. The root cause was narrower and worse than described.

`_column_exists` consulted a HAND-MAINTAINED allowlist of nine table names that
had drifted: `codex_usage`, `gemini_usage` and `migrations` were all migrated by
the module and none was on the list. An unmatched table returned **False** —
"the column does not exist" — when the truth was "I cannot tell", so the ALTER
ran, hit `duplicate column name`, and was recorded as a swallowed failure.

That is the same polarity error as the money surfaces, inverted: there, unknown
provenance must not count as production; here, an unknown table must not count
as a missing column. Both are "I don't know" rendered as a confident answer.

The allowlist is gone. Injection safety now comes from a strict identifier
pattern plus a PARAMETERISED `sqlite_master` lookup — neither of which can
drift, because neither is a list.

Measured: **2 fail-open events per database open → 0 across three opens.**

**The red-check taught something.** Removing the S2 guard alone left the
counter at zero; removing the S6 fix alone did too. Only removing BOTH produced
4 events and failed the test. The two fixes are independently sufficient —
genuine defence in depth, not redundancy — and that is now recorded in the test
so neither is deleted as surplus.

### S2's criterion was imprecise, and its own test caught it

"A fresh database reads zero" is the wrong frame for two of the seven
counters. `capture_outcomes` and `ledger_events_dropped` live in
PROCESS-GLOBAL memory, not on disk — a new database says nothing about them,
and in a long-lived pytest process they legitimately carry whatever earlier
tests recorded. The test passed alone and failed after the suite.

The property S2 actually wants is **"zero when nothing has happened yet"**, and
what "yet" means depends on where the counter lives: a fresh STORE for the
persistent ones, a fresh PROCESS for the in-memory ones. Both are now reset
before the assertion, so it means the same thing for all seven.

Worth recording because the criterion is carried forward as a completion
condition for the next audit. Stated as "a fresh database reads zero" it would
have been satisfiable by a counter that never resets at all.

## S3 — parity test DONE, behaviour change DEFERRED, and a new defect found.

The contract already existed: `auto-route.py` sets `write_pending = False` for a
context-dependent prompt, with a comment naming the exact failure observed
("the throwaway-llm_query dance … then Claude did the real work anyway — double
cost"). Somebody found and fixed it; nothing asserted it, so nothing noticed
when a turn produced two verdicts anyway. Now pinned by AST.

**NEW FINDING — the detector over-fires, and the workaround hid it.**
`is_context_dependent("write a regex that validates an email address")` returns
True. `enforce-route.py` deleted its own re-check for precisely this reason
("over-fired on incidental deictics"). **The consumer was removed; the detector
was never fixed**, so every remaining consumer still over-fires — including the
`write_pending = False` suppression, which now suppresses enforcement for
prompts a routed model could answer.

Opposite polarity to the bug that motivated S3, same root cause: one detector,
two consumers, no shared test. Carried as `xfail(strict=True)`.

`research` stays a QA task type. `_bash_exempt_from_hold`'s docstring is right
that the fix belongs in the classifier, and that is a routing-behaviour change.

## S4 — MECHANISM IDENTIFIED. Not fixed, deliberately.

The escape valve is not misconfigured. The reward is doing its job:

    expected_value = success_rate * ANSWER_VALUE_USD - avg_cost

`avg_cost` is DOLLARS. Every local model costs zero dollars, so the cost term
vanishes for all of them and the comparison collapses to success rate alone.
A 30B model has a higher success rate than a 6.6B one, so **"pick the largest
free model" is exactly what this formula maximises.**

**CORRECTION (2026-09-23) — the sentence above is FALSE.** Measuring it is what
showed that. On `routing_decisions`, the table `aggregate_stats` actually
reads:

    ollama/lfm2.5:8b          n=99  succ 1.000  $0  10111ms  EV 0.05000  <- wins
    ollama/qwen3-coder:30b    n=95  succ 0.926  $0  13674ms  EV 0.04632

The **8B model wins.** The cost term vanishing means SUCCESS RATE decides, and
on this machine that favours the smaller model, because the 30B's success rate
is 0.926 against the 8B's 1.000. The mechanism was right; the prediction was
backwards.

Two further errors in the same analysis, recorded because the habit matters
more than the conclusion: I read the `usage` table (286 rows, all success=1,
all cost 0) and concluded the reward was a CONSTANT — the bandit does not read
that table. And `avg_latency_ms` is not "collected and unread"; it is already
SELECTed in the aggregate query, unused by `expected_value` only.

### S4a — what survived, and it is worse

    openai/gpt-4o           latency: 1 distinct [500.0..500.0]  cost: 1 [0.01..0.01]
    anthropic/claude-opus   latency: 1 distinct [500.0..500.0]  cost: 1 [0.01..0.01]
    ollama/lfm2.5:8b        latency: 99 distinct [1384..55437]  cost: 1 [0.0..0.0]

**1,387 paid-model rows carry identical placeholder values** — exactly 500 ms,
exactly $0.01. Those are not measurements. The local model has 99 distinct real
latencies.

The reward therefore compares MEASURED local models against CONSTANT-STAMPED
paid ones. Adding a latency term now would let a 500 ms placeholder beat a
10-second measurement — optimising a recording defect rather than a model.

**S4a (fix the recording) strictly precedes S4b (use the measurement).** This
is the same ordering S1/S2 established: until the instrument is trustworthy,
nothing computed from it is evidence.

**And the cheap half is already measured:** `avg_latency_ms` is a REQUIRED field
on every `ModelStats` row, and `expected_value` does not read it. Data
collected, nothing reading it — the CLASS-A shape R12 was built for, sitting in
the reward function.

Not fixed here: adding a term changes which model every route picks, and that
needs evaluating on the target distribution rather than on one anecdote.

## S5 — DONE, and it was live.

Testing for it found **83 occurrences of the operator's real home directory**
across `audit/` and `Docs/` in a public repository, 63 in one archived file.
All redacted. Enforced by `tests/test_s5_audit_output_carries_no_identity.py`.

## S7 — DONE, and the reported instance was one of four.

`rich.text.Text(...)` does not parse markup; `Text.from_markup(...)` does.
Fixing the header exposed **30 more literal tokens** from three other call
sites in the same file. The test asserts on the whole rendered output and on
the AST of every `Text(` call, because the reported line was the visible
symptom of a class.

## S8 — the framing was wrong; the defect is ~100x bigger than the row.

Measured before fixing. Only the **gateway** is order-sensitive (10/14 on a
14-pair paraphrase corpus); `ROUTER_POLICY` and `HOOK_POLICY` are already 0/14.

The prompts score **zero in every category**, so `policy.low_signal_default`
decides — `"query"` for hook/router, `"analyze"` for the gateway. The hook is
right by luck, not by measurement.

Over **n=1571** real prompts (CLAUDE.md drop rules first): **41.4%** score 0,
**49.8%** are decided by the default, and the gateway and hook return a
**different** task type for **49.8%** of them.

`ClassifySignal.confident` recorded this from the day it was added and had
**zero readers in `src/`** — the CLASS-A shape, in a ninth place.

**Fixed:** `classify.low_signal_classifications()` → `(decided_by_default,
total)`, registered in `counter_registry`, rendered by `doctor`, alarming on
the *share*, and `0 of 0` reads as Unknown rather than a clean 0%.

**Parked, with numbers:** both candidate routing fixes were measured and
refused. Adding `(?:tell|show) me (?:what|how|…)` to the query intent takes
gateway order-sensitivity 10/14 → 2/14 but pulls negatives into `query` 0/8 →
2/8 (gateway) and 2/8 → **4/8** (router/hook). Flipping the gateway default
re-routes half its traffic on no evidence. The route is unchanged, so the K4
`xfail(strict=True)` **stands**.
