## P09-12. The proxy's tier decision repeated body-sized work on every classified call

- **Symptom.** Live turn-first decisions (`~/.llm-router/proxy_calls.jsonl`, turn_first,
  ts >= 2026-10-08T19:58Z, n=133) had p95 54.3 ms against the 50 ms P0.9-e bar. The tail was
  `classify` (p50 2.66, p95 47.9, max 234.6 ms, n=59) and `haiku_checks` (p50 2.97, p95 61.0,
  max 68.7 ms, n=59). The over-bar rows cluster in two windows (2026-10-08 20:13-20:41Z and
  22:09-22:18Z) in which the sync hooks' own latency was also 2-6x its usual value, so machine
  contention multiplied the decision's CPU time; the decision's own work set how much there was
  to multiply.
- **Cause.** Three per-call costs that grew with the request:
  1. `haiku_checks` ran `haiku_block_reason`, which serializes the whole body
     (`_approx_context_tokens`, `json.dumps` of messages, system and tools: 1-12 ms on the
     0.5-2.8 MB bodies Claude Code sends), on every classified call, although its verdict is
     read only when the Haiku tier is considered. When the classifier proposed Haiku, the proxy
     ran it a second time for the ledger's `tier_haiku_block`; with `haiku_rewrite` and quota
     pressure on, a third time.
  2. `classify` scored up to 3,000 characters with 18 IGNORECASE regexes (re cannot use its
     literal fast paths under IGNORECASE: ~1.2 us/char) and ran the capability detector
     (~25% of the phase), whose result the tier decision discards.
  3. With `--steps off` (the live mode) nothing imported `llm_router.classify` before the first
     classified call, so every proxy start paid ~8 ms of import inside that call's `classify`.
- **Fix.** (1) The Haiku body check is lazy and memoized per decision (`tiers._HaikuBlock`,
  `_Lazy`): it runs at most once, only when a step considers the Haiku tier, and the proxy
  reuses its verdict (`TierDecision.haiku_block`) for `tier_haiku_block`. (2)
  `classify_signals(..., capabilities=False)` for the tier decision, and `_score_categories`
  runs case-sensitive twins of the patterns on ASCII-lower-cased text, falling back to the
  originals when the text holds one of the four non-ASCII characters that fold to an ASCII
  letter. (3) `build_app` imports the classifier at start when tiers are on. No decision or
  score changes; no work moved into an unmeasured span on the request path (the import moved to
  start-up).
- **Test.** `tests/test_p09e_decision_work.py`: 8 of its 13 tests fail on main 7aaf8c96 and pass
  here: the body check never runs for a non-Haiku target, runs once for a Haiku proposal and is
  reused by the ledger row; the capability detector is not run; the classifier is imported at
  start; twin coverage; the fold set; and 19,440 decisions over every policy switch, quota
  pressure, model, thinking, class, prior sticky model and body shape are identical lazy vs eager
  (on main it fails only because `_Lazy` does not exist; an independent run of the same grid on
  main's code and on this branch gave byte-identical decisions and sticky state). The other 5
  pass on both by design: twin scores equal IGNORECASE scores on 404 texts per seed (4 seeds), and
  with `haiku_rewrite` off the proxy still records `tier_haiku_block`.
  Benchmark: `scripts/bench_proxy_decision.py --runs 300` (warm) and `--runs 200 --cold`.
