**Test-isolation fix required to reach a genuinely-green suite (WS9).** The 5 new
`TestBoundedOperationalShadowWiring` tests initially failed *intermittently* — passing
in isolation but failing when the full suite ran, with the surviving routing chain
collapsing to a single real-host-derived model (`codex/gpt-4o-mini`) instead of the
`mock_env`-configured chain the tests expected. Root cause: `llm_router/server.py` runs
`dynamic_routing.initialize_dynamic_routing()` at **module import time** (not inside a
function), so the first time any earlier-alphabetically-collected test file imports
`llm_router.server` (e.g. `tests/test_route.py`, collected before `tests/test_router.py`)
it permanently populates the plain-module-global `dynamic_routing._dynamic_routing_table`
from the *real host machine's* available providers. That cache is immune to
`monkeypatch.setenv()`-based env mocking, so `router.py`'s
`_build_and_filter_chain()` → `get_dynamic_model_chain()` lookup silently returned the
stale real-environment chain instead of falling back to the static, `mock_env`-driven
one — explaining both the intermittency (order-dependent) and the observed single-item
chain. **Fix**: `TestBoundedOperationalShadowWiring`'s autouse fixture now saves
`dynamic_routing._dynamic_routing_table`/`_discovery_complete`, calls
`dynamic_routing.reset_dynamic_routing()` before each test (forcing the static fallback
path `mock_env` expects), then restores the saved globals after `yield` — a test-only
change with zero production-code impact, so it does not appear in §1's capability
table. Verified passing both in isolation and as part of the full 2721-test suite.

## 6. Disclosed gaps / unsupported claims

Being explicit about what is **not** true, so nothing here is taken on faith:

1. **`LLM_ROUTER_QUALITY_FEEDBACK` was never implemented and never will be, by design —
   this is settled, not an open gap.** An earlier draft of the migration plan named this
   flag, but the heuristic quality scorer's `should_skip_model()` call in `router.py`'s
   fallback-chain path is unconditional — it predates this migration (pre-existing
   functionality), is unrelated to the LoopHole-verdict additions elsewhere in this
   release, and is already always-on in production. Gating it now would silently change
   existing routing behavior for every current install, which is a worse outcome than
   leaving it ungated. **Resolution (WS9): the plan/docs reference has been corrected, not
   the runtime** — the flag does not appear in the §5 inventory (it never did), and every
   doc that previously implied it existed or was pending has been updated to state plainly
   that the check is unconditional by deliberate choice.
2. **`audit_routing.py::run_audit()` now has an invocation path (WS9).** The
   `llm-router audit` CLI subcommand (`commands/audit.py`) calls it, respects
   `LLM_ROUTER_AUDIT_DISABLED`, and renders sampled/audited counts plus verdict breakdown
   (`--json` and `--limit` supported). It remains strictly read-only/reporting — it never
   mutates routing state. Covered by `tests/commands/test_audit.py`, including a
   brand-leak guard consistent with the existing `TestBrandLeak` pattern.
3. **`bounded_operational.py::should_route_bounded()` is now wired (WS9),
   flag-gated, default off.** Called from the live routing decision path in `router.py`
   strictly behind `LLM_ROUTER_BOUNDED_OPERATIONAL`. With the flag unset/false the
   routing path is byte-identical to before — proven by an invariance test
   (`test_invariance_flag_absent_vs_present_but_disabled`) that compares route decisions
   with the module absent vs. present-but-disabled. Enabled-path behavior (qualifying and
   non-qualifying cases, including the non-`simple`-complexity case) is covered by
   dedicated tests in `tests/test_router.py::TestBoundedOperationalShadowWiring`. These
   tests initially exhibited order-dependent flakiness caused by a pre-existing
   test-isolation gap (a module-global dynamic-routing cache populated once from the
   real host environment on first import of `llm_router.server`, immune to
   `mock_env`); this was root-caused and fixed with a test-only save/reset/restore
   fixture pattern — see §2 for the full diagnosis. No production code changed as a
   result; `dynamic_routing.py`'s caching design is correct for real server operation,
   the gap was solely the absence of a test-side reset.
4. **Real-database-copy migration replay was performed in WS9.** The forward migration
   (`cost._get_db()` + `execution_ledger._connect()`) was run against a byte-verified copy
   of the real, populated `~/.llm-router/usage.db` (948 pre-existing `claude_usage` rows,
   301 `model_quality_trends` rows, 904 `routing_decisions` rows). Resulting schema matches
   a fresh install exactly, all pre-existing row counts are preserved, and a second run is
   a verified no-op. See §9 for the full procedure and output. This supersedes and closes
   the earlier gap; the synthetic idempotency tests (`test_migration_idempotent`,
   `test_connect_twice_is_idempotent`, `test_migrates_pre_migration_table`) still pass and
   now sit alongside the real-data replay rather than standing in for it.
5. **Performance benchmarking was run in WS9.** The hot, synchronous routing-decision
   function (`router._resolve_profile`) was micro-benchmarked (5000 iterations, warmed up)
   on `main` and on `feature/chuzom-capabilities`, on the same Python 3.12.13 interpreter,
   with all new flags left at their default (off) state. Median per-call latency was
   statistically indistinguishable between branches (well under the 5% regression
   threshold — see §10 for exact numbers). The new WS9 flag-check itself
   (`bounded_operational_enabled()`) was also measured directly and costs a fraction of a
   microsecond, confirming the flag-gated wiring adds no measurable overhead to the default
   path.
6. **Two pre-existing, out-of-scope findings noted but deliberately left unfixed.**
   Neither is a WS9 blocker, neither was introduced by this migration, and fixing either
   would be a behavior change outside this workstream's "no behavior changes" mandate —
   both are recorded here for visibility, not as open blockers:
   - `profiles.py::reorder_for_pressure()`'s docstring describes BUDGET-profile
     quota-pressure reordering behavior that does not match what the function actually
     does for that profile. Pre-existing, unrelated to any ported capability.
   - `router.py`'s codex-dispatch branch (`elif provider == "codex":`) does not re-check
     `is_codex_available()` at dispatch time (the check happens earlier, during chain
     construction). Pre-existing, unrelated to any ported capability; a race between
     chain construction and dispatch would need to be contrived to trigger it.

No other capability claims in the WS1–WS7 commit messages were found to be false during
spot-checking. All five blockers were closed in WS9 (see `CHANGELOG.md`'s v11.1.0
entry, now updated accordingly; full procedures and output in §9 and §10 below).

the byte-identical pre-migration copy taken above is exactly such a backup,
and restoring it (`cp` back over the live path) fully reverts the schema and
data with no partial-migration risk, since the forward migration never
deletes or destructively alters existing columns/tables in the first place.

**Conclusion**: Blocker 4 is closed. The migration is safe to run against a
real, pre-existing production-shaped database: schema converges to the same
result as a fresh install, no data is lost or altered, re-running is a true
no-op, and there is no destructive path to guard against in the first place.

## 10. Performance benchmark (WS9)

**Goal**: prove the default routing path (all new WS9 flags left unset/off) is not
slower on `feature/chuzom-capabilities` than on `main`.

**Tooling**: `pytest-benchmark` is not installed in this project
(`uv run --frozen python -c "import pytest_benchmark"` fails), so a small, committed
`timeit`-style harness was written instead, as explicitly permitted by the task:
[`scripts/benchmark_routing_decision.py`](../../scripts/benchmark_routing_decision.py).
It warms up 200 calls then times 5000 iterations per function, reporting
median/p95/mean/min/max in microseconds, plus the git revision and Python version of
the run for traceability.

**Benchmarked functions**:

1. `llm_router.router._resolve_profile` — the pure, synchronous function every
   `route_and_call` invocation uses to resolve `(profile, complexity, use_thinking)`
   from the prompt/hints/config. It is **unmodified by WS9** and exists identically on
   both branches, so it serves as a direct, apples-to-apples control for "did the
   default path regress." Called across representative SIMPLE/MODERATE/COMPLEX-length
   prompts with no explicit profile, complexity hint, or classification data (the
   cheapest, most common call shape).
2. `llm_router.bounded_operational.bounded_operational_enabled` — the new WS9 flag
   check that `_dispatch_model_loop` now calls once per model attempt on the default
   (flag-off) path. This function does not exist on `main` at all, so it cannot be
   diffed branch-to-branch; instead its absolute cost is reported to show the new
   gate itself is negligible.

**Procedure**: the harness was run on `feature/chuzom-capabilities` in place, then a
disposable, non-destructive `git worktree` was used to get a clean `main` checkout for
a directly comparable run, then torn down:
